================================================================================
/v1/chat CONNECTION GUIDE — for a developer wiring a low-latency chat client
to this Agent. Read this whole file before writing code; the "common
mistakes" section at the bottom is every integration bug this repo has
actually hit in practice, not hypothetical ones.
================================================================================

--------------------------------------------------------------------------------
0. WHAT THIS API IS — READ THIS FIRST
--------------------------------------------------------------------------------
  - ONE MESSAGE IN, ONE FULL REPLY OUT. It is a single blocking request/
    response call, not a streaming API. There is no SSE, no chunked/
    token-by-token output, no WebSocket. You send one message, you get the
    complete reply back in one JSON payload once the model has finished
    generating it. If your product needs a "typing" / streaming UI, you
    build that illusion client-side (e.g. reveal the finished text
    progressively) — the server gives you nothing to stream from.

  - STATELESS. There is no server-side conversation memory, no session id,
    no history parameter. Every call carries exactly {"message", "role"}.
    If your chat needs multi-turn context, YOU maintain the transcript on
    your own server/DB and decide what (if anything) to fold into the next
    "message" string — this API will not remember anything between calls.

  - SERIALIZED. The whole API allows exactly ONE request in flight at a
    time, system-wide, across every client and every role (see section 5).
    This is the #1 fact that shapes a "low latency" integration: you are
    not building a client against a scalable pool, you are building a
    client against a single shared lane.

--------------------------------------------------------------------------------
1. BASE URL / TRANSPORT
--------------------------------------------------------------------------------
  https://<host>:8001        (one port for everything: dashboard, /v1/chat,
                               /v1/graphql, /v1/top-complaints, /v1/health)

  TLS is normally on with a SELF-SIGNED certificate. Your HTTP client must
  be told to trust it, or every request fails before it even reaches this
  API's code:

    - Node / anything using system CA trust: point it at the issued CA/cert
      file (e.g. NODE_EXTRA_CA_CERTS=/path/to/agent.pem for Node's fetch).
    - Whatever your stack's equivalent is (REQUESTS_CA_BUNDLE for Python
      `requests`, etc.) — set it in every environment that calls this API,
      including your own laptop/manual test runs, not just the deployed
      service. A process launched manually without that env var set will
      fail EVERY signed call in ~20-30ms with a generic connection/TLS
      error. That is indistinguishable from "the agent is down" unless you
      already know to suspect TLS trust first — see section 8.

  Get the actual cert / CA bundle from whoever administers this Agent
  instance. HMAC signing (section 3) is unaffected by TLS either way — the
  signature never covers the URL or scheme.

--------------------------------------------------------------------------------
2. GETTING A CREDENTIAL
--------------------------------------------------------------------------------
  Ask the Agent's administrator (dashboard Settings page, Administration
  role) for an `ext-*` client_id + secret pair, and tell them exactly which
  of the five roles (section 4) your app needs to send. The secret is shown
  ONCE at creation — get it into your secret manager immediately, it is
  never re-displayed.

  IMPORTANT — verify this before writing a single line of client code: ask
  the administrator to confirm your credential's allowed-roles list
  actually contains every role value your app intends to send. A role can
  be one of the five valid values and STILL get rejected with
  403 role_not_allowed if your specific credential wasn't granted it. This
  is a real bug another integration hit in production: a credential
  provisioned for `end_user` only received a request mapped to `l3`
  (administrator) and got silently swallowed as "assistant unavailable"
  because the caller didn't log the rejection. Don't assume — confirm.

--------------------------------------------------------------------------------
3. AUTH — HMAC SIGNING (not bearer tokens, not API keys on the wire)
--------------------------------------------------------------------------------
  Every /v1/chat and /v1/graphql request needs three headers:

    X-Client-Id   your ext-* client id
    X-Timestamp   current unix time, seconds, as a string
    X-Signature   hex(HMAC-SHA256(secret, "<timestamp>." + raw_body_bytes))

  Rules that WILL bite you if ignored:

    - Sign the EXACT bytes you put on the wire. Serialize your JSON body
      once; sign those bytes; send those bytes. Re-serializing between
      signing and sending (different key order, different whitespace) is
      the single most common integration bug — the signature will no
      longer match what the server hashes, and you'll get 401
      bad_signature with no other clue why.
    - X-Timestamp must be within 300 seconds of the server's clock, in
      EITHER direction. Keep your host's clock NTP-synced.
    - GraphQL: sign the entire GraphQL request body (the whole
      {"query":...,"variables":...} JSON), not just the message/role
      variables.
    - A GET request (no body — only /v1/health and /v1/top-complaints are
      GET) signs an empty string: hex(HMAC-SHA256(secret, "<timestamp>.")).

  Reference (bash):
    ts=$(date +%s)
    body='{"message":"how do I reset my VPN?","role":"end_user"}'
    sig=$(printf '%s.%s' "$ts" "$body" | openssl dgst -sha256 -hmac "$SECRET" | sed 's/^.* //')
    curl -X POST https://<host>:8001/v1/chat \
      -H "X-Client-Id: $CLIENT_ID" -H "X-Timestamp: $ts" -H "X-Signature: $sig" \
      -H "Content-Type: application/json" -d "$body"

--------------------------------------------------------------------------------
4. REQUEST / RESPONSE SHAPE
--------------------------------------------------------------------------------
  REST — POST /v1/chat
    Request:  { "message": "<string, non-empty>", "role": "<see below>" }
    Success (200): { "reply": "<string>", "role": "<canonical role used>" }
    Failure: always { "error": "<code>" } — see section 6 for the full table.

  GraphQL — POST /v1/graphql (same auth, same gates, same error meanings,
  just wrapped in GraphQL's own response/error shape)
    mutation chat(message: String!, role: String!): V1ChatReply!
    type V1ChatReply { reply: String!, role: String! }
    GET /v1/graphql in a browser serves GraphiQL for schema browsing only —
    running `chat` still needs valid HMAC headers.
    Failures come back as one entry in errors[]:
      { "errors": [ { "message": "server_busy",
                       "extensions": { "code": "server_busy", "status": 429,
                                       "retryAfter": 2 } } ] }

  ROLE VALUES — must be one of exactly these five (the audience the model's
  fixed guidance is tuned for; you cannot inject your own instructions):
    end_user | l1 | l2 | l3 | security

  This gate ALSO accepts a small set of aliases and translates them to the
  five values above before checking anything else, so you can send your own
  org's role names directly instead of translating client-side:
    "user"                      -> end_user
    "it_admin"                  -> l1
    "org_admin"                 -> l2
    "administrator" / "admin"   -> l3
  Matching is case-insensitive and treats spaces as underscores
  ("Org Admin" == "org_admin"). Anything not in the five canonical values or
  this alias list gets 400 bad_role.

  >>> KNOWN CONVENTION MISMATCH — CONFIRM, DON'T ASSUME <<<
  At least one other production integration against this Agent maps its own
  "ORG_ADMIN" role to l1 (not l2). This file's alias table maps org_admin to
  l2. Both are valid canonical roles — the point is these mappings are a
  local convention, not something derivable from the API. Before wiring your
  role mapping, confirm with the Agent's administrator (or just do the
  translation yourself and send end_user/l1/l2/l3/security directly) which
  canonical role each of your app's user types should resolve to, and get
  your credential's allowed-roles list to match.

--------------------------------------------------------------------------------
5. CONCURRENCY & LATENCY BUDGET — the part that determines "low latency"
--------------------------------------------------------------------------------
  - GLOBAL CONCURRENCY CAP = 1. Only one /v1/chat or /v1/graphql call is
    processed AT A TIME, across every client_id and every role combined —
    it's one shared local model process behind this API, not a pool. A
    second call arriving while one is in flight is refused immediately with
    429 server_busy (Retry-After: 2), it is NOT queued for you.
    Design consequence: never fire concurrent chat requests, from one user
    or across users. Serialize calls client-side (one in flight per app,
    ideally one in flight across your whole deployment) and treat 429 as
    "wait 2s and send exactly one retry," not as a signal to fan out more
    attempts.

  - NO PER-CLIENT RATE LIMIT beyond that shared cap — you won't get
    throttled for calling frequently, only for calling concurrently while
    another call anywhere is still running.

  - TIMEOUTS — set your HTTP client's read/response timeout to AT LEAST
    180 SECONDS. That's this server's own ceiling for the upstream model
    call; a real reply can legitimately take anywhere from ~2-5 seconds
    (short answers, observed in practice) up to that ceiling for a long
    one. A client timeout shorter than 180s will produce spurious failures
    on requests that were actually still succeeding server-side.

  - CONNECTION REUSE — keep HTTP keep-alive on and reuse the connection
    across calls. A fresh TCP+TLS handshake on every request (especially
    against a self-signed cert) is pure added latency with zero benefit,
    given you can only have one call in flight anyway.

  - There is no faster path than the above: this is a synchronous,
    single-lane API. The only levers you control for perceived latency are
    (a) not adding your own retry storms on top of the 2s backoff, (b) not
    paying handshake cost per request, and (c) giving the user real
    feedback while the one in-flight call is still running instead of
    firing a second one.

--------------------------------------------------------------------------------
6. ERROR CODES — full table, REST status + GraphQL extensions.code alike
--------------------------------------------------------------------------------
  Status  error                Meaning / what to do
  ------  -------------------  --------------------------------------------
  400     bad_timestamp        X-Timestamp isn't a valid integer — fix your
                                client, don't retry as-is.
  401     stale_timestamp      Timestamp outside the 300s skew window — sync
                                your clock; don't retry until it's fixed.
  400     malformed_signature  X-Signature isn't 64 hex chars — client bug.
  401     bad_signature        Signature doesn't match the body you sent —
                                usually the "re-serialized after signing"
                                mistake (section 3). Not something to retry
                                blindly; find the mismatch first.
  401     unknown_client       X-Client-Id missing/not found, or the
                                credential still has its placeholder secret.
  400     bad_request          Body isn't valid JSON, message/role aren't
                                strings, or message is empty.
  400     bad_role             role isn't one of the five values or a known
                                alias (section 4).
  403     role_not_allowed     role is valid but not in YOUR credential's
                                allowed-roles list — a permissions/config
                                issue, not a code bug. Go back to section 2.
  429     server_busy          Global concurrency cap hit. Retry-After: 2
                                (also in the body as retry_after). Wait,
                                then retry once — see section 5.
  502     upstream_error       The local model server hiccuped. Safe to
                                retry once with a short backoff.

  Every failure on /v1/chat, /v1/graphql, /v1/health and /v1/top-complaints
  uses this exact {"error": "<code>"} shape (or the GraphQL errors[]
  equivalent) — never a differently-shaped error body, never HTML.

--------------------------------------------------------------------------------
7. GET /v1/health and GET /v1/top-complaints (for completeness)
--------------------------------------------------------------------------------
  GET /v1/health          no auth, always {"status":"ok"} — liveness only,
                           tells you nothing about model/DB health.
  GET /v1/top-complaints  same HMAC scheme as above but a SEPARATE
                           credential set (no roles), read-only, returns up
                           to 7 categories: {"top_complaints":[{"category":
                           "...","count":N}, ...]}.

--------------------------------------------------------------------------------
8. INTEGRATION MISTAKES ALREADY SEEN IN PRODUCTION — check your code against
   this list before shipping
--------------------------------------------------------------------------------
  a) Self-signed cert not trusted when the calling process is run manually
     (works fine under its normal service manager because the CA env var is
     set there, fails the moment someone runs it by hand for a quick test).
     Symptom: every signed call fails in ~20-30ms. Looks exactly like "the
     agent is down." It's TLS. Check section 1 first, always.

  b) Swallowing a non-200 response into a generic user-facing message
     ("assistant unavailable") without logging the status code / error
     field anywhere. This turns a one-line diagnosis (403 role_not_allowed,
     credential X missing role Y) into an unexplainable ghost that looks
     like a random outage days later. Log status_code + error on every
     failure, every time, even in the fast path.

  c) Assuming role X is authorized just because it's one of the five valid
     values. Valid and allowed are two different checks (bad_role vs.
     role_not_allowed) — confirm your credential's actual allowed-roles
     list, don't infer it from the role names being "obviously fine."

  d) Firing a second chat request (e.g. a retry, or a second user action)
     while the first is still in flight. With global concurrency = 1 this
     doesn't run in parallel, it 429s. Serialize on the client.

  e) Re-serializing the JSON body between computing the signature and
     sending the request (different library, different key order,
     pretty-printing added). Sign the literal bytes you transmit, once.
