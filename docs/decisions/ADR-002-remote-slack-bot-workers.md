# ADR-002: Remote Slack bot workers — reverse control plane

## Status

Proposed.

## Date

2026-09-18

## Context

`SlackManager` (`server/src/modules/slack-bots/slackManager.ts`) owns every live bot
connection inside the API process: it opens the Socket Mode WebSocket, bridges
messages to the Analytics Agent, and persists status. That forces every Slack bot
into the platform's own network. Clients that must run their bot inside *their*
network (an on-prem DMZ, a separate VPS, an air-gapped site) have no story, and the
admin dashboard can only ever see bots that share the platform's host.

The constraint that shapes everything below: **a foreign network will not open an
inbound port to us, and we will not ship a plaintext token across it.** So both
channels — the bot's to Slack and the bot's to us — must be outbound from the bot:

- Socket Mode is already outbound (`wss://` to Slack), which is why it exists.
- The control plane must therefore be a *reverse* control plane: the worker calls
  home over HTTPS, and the platform answers commands only through responses/polls on
  those outbound connections. No inbound listener on the platform's behalf either —
  the platform is the one server we fully control, so it can hold an inbound web
  surface, but the worker must never need to reach it at anything but 443.

The threat model that the design answers:

1. A stolen per-bot machine credential must not read or mint anything outside its
   own bot, and must not fetch another bot's keys.
2. Tokens arrive at a worker that lives in a customer's network. They must be
   delivered once, over TLS, and never touch disk in plaintext.
3. A worker registering the same bot twice (two instances, duplicate connections)
   must be detected — Slack delivers events to every open Socket Mode connection.
4. Admin "disable" and token rotation must reach the worker within one heartbeat
   and stop it from acting.
5. Everything the dashboard already shows (`status`, `lastCheckedAt`, `lastError`)
   keeps working without UI change.

## Decision

### 1. Each bot runs in its own worker process in its own network

One worker = one SlackBot, by construction. Two workers = two Socket Mode
connections = duplicate event delivery, which Slack has no way to arbitrate away.
`ponytail:` one worker per bot; a daemon hosting N bots on one host (a "bot farm")
is a follow-on — its only real problem is guarding against running the same bot
twice, and the instance guard in §5 already catches it.

The worker reuses the existing `slackManager` logic almost verbatim, with one change:
instead of calling the Analytics Agent directly it **forwards the message to the
platform**, which runs `agentChat` and returns the reply. The worker transiently
holds the message in flight but stores nothing; agent credentials never leave the
platform network, and every conversation is visible to the platform's auditing.

### 2. Outbound-only control plane

Three endpoints, all `POST`, all authenticated as in §3:

| Endpoint | Purpose |
|---|---|
| `POST /api/bot-worker/:botId/provision` | First call. Returns the bot + app tokens (decrypted server-side, over TLS). Succeeds once. |
| `POST /api/bot-worker/:botId/heartbeat` | Periodic (default 30s, same cadence as today's poll). Carries `{status, socketConnected, lastEventAt, msgCount, instanceId, version}`. Response carries pending commands (`reconcile`, `disable`, `rotated`). Persists `status`/`lastCheckedAt`/`lastError` exactly like `slackManager` does today, so the dashboard is unchanged. |
| `POST /api/bot-worker/:botId/message` | A Slack message (or block-action payload) to run through the agent; returns the reply text the worker posts to Slack. |

Commands ride in the heartbeat response rather than a separate poll — one
round-trip, nothing to keep in sync. The worker trusts commands because they are the
response to its own authenticated request over TLS 1.3. `ponytail:` no per-command
HMAC on the response; add one only if a threat model ever includes a local network
that can defeat TLS (at which point TLS pinning is the right move, not HMAC).

### 3. Per-bot worker credential, provisioned once

A new key kind, deliberately separate from the existing AD-automation key
(`adk_`, `apiKeyHash`) so the two capabilities can be revoked independently:

- `wrk_…` key, generated by a new admin endpoint next to `generateApiKey`, shown
  once, stored as SHA-256 (`hashApiKey`, existing) in a **new `workerKeyHash`
  column**. The provisioning/heartbeat endpoints match the `wrk_` prefix against
  `workerKeyHash` only; `/api/ad-ingest` keeps checking `apiKeyHash` only. No scope
  matrix, no shared-key coupling.
- Provisioning sets `provisionedAt`. A second `provision` with the same key is
  refused (`409`) — re-provisioning is the admin **Rotate** flow: regenerate
  `wrk_`, call provision again. Rotating the Slack tokens (existing `updateBot`)
  flips a `rotated` flag the next heartbeat collects, so the worker re-provisions
  and re-pulls.
- Each request is additionally HMAC-signed with the **Scheme B** timestamped
  signature pattern already proven in `agentApi.ts` (`signSchemeB`) — a captured
  request cannot be replayed against a later clock or a different body.

Requests are rate-limited behind the same wall that already guards `/api/ad-ingest`,
and every call is audited with the existing `audit()` helper.

### 4. Token handling on the worker

The provision response is the only time the worker ever sees plaintext tokens.
It stores both with the existing AES-256-GCM scheme (`encryptSecret`/`decryptSecret`)
under a **local** key (`WORKER_TOKEN_SECRET`, or whatever the host keystore offers),
so plaintext is never written to disk. `disable`/`rotated` commands wipe the vault
and disconnect.

### 5. Instance guard

The heartbeat carries `instanceId` (a UUID minted at worker boot). The platform
records it on `slackBots.activeInstance`. A heartbeat whose `instanceId` differs
from the recorded one gets a `disable` in the response — the active instance wins,
the duplicate kills itself. Combined with one-worker-per-bot, this is the complete
answer to §Context #3.

### 6. Data model (all on the existing `slackBots` table)

```sql
ALTER TABLE "slackBots" ADD COLUMN "workerKeyHash"    TEXT;          -- SHA-256 of wrk_… key
ALTER TABLE "slackBots" ADD COLUMN "workerKeyHint"    TEXT;          -- masked hint (see maskToken)
ALTER TABLE "slackBots" ADD COLUMN "workerProvisionedAt" TIMESTAMPTZ;  -- one-time gate
ALTER TABLE "slackBots" ADD COLUMN "activeInstance"   TEXT;          -- last heartbeating worker
```

### 7. Migration, not cutover

A bot is worker-owned if `workerKeyHash IS NOT NULL`, otherwise it stays on the
platform-owned `slackManager` path — both transports coexist, `connect`/`disconnect`
in the UI routes to whichever owns the bot.

- Phase 1: run the worker as a separate process on the platform host against a
  test bot. Proves the boundary without touching the network.
- Phase 2: first foreign-network deployment, onboarding doc + the provision flow.
- Phase 3: dashboard gets a per-bot "worker" badge from `activeInstance`/`workerKeyHint`.

Rollback is one flag: clear `workerKeyHash`, bot falls back to `slackManager`.

## Consequences

- Clients (i.e. the customer) must run a worker process — a small Node box that
  needs outbound 443 to Slack and to the platform only, no inbound ports anywhere.
- Posting a reply costs one extra platform round-trip per message (~single-digit ms
  on 443; nothing on the platform→agent budget that doesn't already exist).
- Two key columns instead of one shared column — kept separate on purpose so a
  leaked AD key cannot fetch tokens.
- Duplicate-instance protection is detect-and-kill, not prevent-after-race: the
  two-heartbeat window where both instances are up still delivers events to both.
  Slack has no API to arbitrate this; "one worker per bot" is the actual prevention.

## Alternatives considered

- **Platform pushes config to workers** — rejected: no inbound path to foreign
  networks; a push channel is exactly the inbound hole Socket Mode lets us avoid.
- **Worker calls the agent directly** — rejected: ships `ext-*` credentials to the
  customer network and hides every conversation from platform auditing.
- **Shared-key (adk_ reused for control)** — rejected: the AD key mints temporary
  passwords into the ticket flow; coupling it to token-fetching means one leak
  escalates to full impersonation.
- **Message broker (Redis/Kafka) between platform and workers** — rejected: a
  reachable broker negates the no-inbound constraint or requires yet another VPN;
  3 HTTPS endpoints reuse proven in-repo primitives.
